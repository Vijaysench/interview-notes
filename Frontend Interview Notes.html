    01 JavaScript Essentials

    JavaScript runs in the browser and makes pages interactive. The ideas that keep coming up: how variables are scoped, how values are compared, how functions remember data (closures), and how slow work is handled without freezing the page (async).

    • Use const by default, let when the value changes, avoid old var.
    • Always compare with === (value and type). == converts types first and causes bugs.

    A closure is a function that remembers variables from where it was created, even after the outer function finished — it's why useState can remember values between renders.

    function makeCounter() {
  let count = 0;                 // private to this counter
  return function () {
    count = count + 1;           // "closes over" count
    return count;
  };
}
const next = makeCounter();
next(); // 1
next(); // 2  — count is remembered

    map, filter, reduce turn data into UI constantly:

    const nums = [1, 2, 3, 4];
nums.map(n => n * 2);               // [2,4,6,8]  transform each
nums.filter(n => n % 2 === 0);      // [2,4]      keep some
nums.reduce((sum, n) => sum + n, 0);// 10        one value

    QDifference between var, let, and const?

    Avar is old and leaks outside blocks — avoid it. let is for values that change. const is for values that won't be reassigned. I use const by default.

    Q== vs ===?

    A== compares after converting types, so 5 == "5" is true — bug-prone. === checks value and type. I always use ===.

    QWhat is hoisting?

    AJS moves declarations to the top of their scope before running. var and functions get hoisted; with let/const the name exists but can't be used before its line. Takeaway: declare before you use.

    QWhat is a closure? deep

    AA function that remembers variables from where it was created, even after the outer function finished (the counter example). It's how useState remembers values between renders. ★ yours In my config-driven forms, closures let each field keep its own validation logic.

    QWhat does this refer to?

    AIt depends on how a function is called, not where it's written. Arrow functions borrow this from the surrounding code, which is why I use them in React to avoid binding issues.

    QWhat is the event loop? deep

    AJS runs one thing at a time. Slow tasks (API calls, timers) are handed off, and when they finish their callback goes back in line to run. That's how JS stays responsive without true multithreading.

    02 TypeScript

    TypeScript is JavaScript plus types. You describe what shape your data should be, and the editor warns you before the code runs if something doesn't match. On a big codebase it also works like built-in documentation.

    type Insurer = {
  id: string;
  name: string;
  active?: boolean;        // optional — may be missing
};

let value: string | number;  // union — one of several types
value = "hello";             // ok
value = 42;                  // also ok

    Generics let one function work with many types — think "a box of X":

    function first<T>(items: T[]): T {
  return items[0];           // works for string[], number[], Insurer[]…
}

    QWhy TypeScript instead of plain JavaScript?

    AIt catches mistakes before the code runs and documents what shape of data things expect. ★ yours On a 2,200-file app, that safety net saves a lot of debugging.

    Qtype vs interface?

    ABoth describe object shapes. interface is usually for objects and can be extended; type is more flexible (also unions). Interchangeable for simple objects — I pick one and stay consistent.

    Qany vs unknown?

    Aany turns off type checking — risky. unknown means "not known yet" but forces a check first. I avoid any except as a quick temporary fix.

    QWhat are generics? deep

    AOne function or type that works with many data types — like Array<string> meaning "array of strings." ★ yours My reusable components use generics so they accept different data shapes safely.

    QHow do you use TypeScript day to day?

    AI type component props, API responses, and Redux state. Biggest wins are autocomplete and catching "undefined is not a function" early. I don't over-engineer types.

    03 React — Core & Hooks

    React builds UIs out of components — small reusable pieces. When a component's data changes, React re-renders it and updates only the parts of the screen that actually changed.

    • Props = data passed into a component from its parent (read-only).
    • State = data a component owns and can change over time.
    function Counter() {
  const [count, setCount] = React.useState(0);   // state + updater
  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}

    useEffect runs code after render; the dependency array controls when it re-runs:

    useEffect(() => {
  loadQuote(insurerId);          // run this…
}, [insurerId]);                 // …again only when insurerId changes

    QWhat is React in one line?

    AA JavaScript library for building UIs out of reusable components, where the screen updates automatically when the data changes.

    QProps vs state?

    AProps come from outside (read-only); state lives inside and can change. Rule of thumb: props in, state owned.

    QWhat does useState do?

    AGives a component memory that survives re-renders, plus a function to update it. Calling the updater re-renders with the new value.

    QWhat is useEffect and the dependency array? deep

    AuseEffect runs code after render — for fetching, subscriptions, etc. The array controls when: empty [] = once on mount, [id] = whenever id changes. ★ yours I use it to fetch quote data when the selected insurer changes. Common mistake: a missing dependency causing stale data.

    QWhy does a component re-render?

    AWhen its state changes, its props change, or its parent re-renders. React then updates only the parts of the real screen that changed.

    QWhy do lists need a key?

    AA unique ID that helps React tell list items apart, so it updates the right one instead of redrawing all. Use a stable ID, not the array index, when items can reorder.

    QuseMemo and useCallback? deep

    APerformance tools. useMemo remembers an expensive calculation's result; useCallback remembers a function so it isn't recreated each render. I use them when I see a real performance problem, not everywhere.

    QWhat is a controlled input?

    AAn input whose value is driven by React state — React is the single source of truth. Standard way I build forms so validation and conditional logic stay in sync.

    04 State Management (Redux & Toolkit)

    When many screens need the same data (like a quote in progress), passing it down through every component gets messy. Redux keeps that shared data in one central store any component can read.

    • Store — the single box holding shared state.
    • Action — a message saying "something happened".
    • Reducer — takes current state + action, returns new state.

    Flow: component dispatches an action → reducer updates the store → components using that data re-render. Redux Toolkit is the modern, less-boilerplate way; a slice bundles state + reducers:

    const quoteSlice = createSlice({
  name: "quote",
  initialState: { insurerId: null, product: null },
  reducers: {
    setInsurer(state, action) { state.insurerId = action.payload; },
    setProduct(state, action) { state.product = action.payload; },
  },
});

    QWhy use Redux at all?

    AWhen many parts need the same data, central state keeps it consistent instead of passing props everywhere. ★ yours Quote and proposal data is needed across many screens in my journey app.

    QExplain store, action, reducer in plain words.

    AStore = the one box of shared state. Action = a message that something happened. Reducer = the function that takes state + action and returns new state.

    QWhat is Redux Toolkit / a slice?

    AThe official modern Redux with less boilerplate. A slice bundles a feature's state and reducers in one file. ★ yours I use slices to keep each feature's state organised.

    QRedux vs local state vs Context?

    ALocal useState for one-component data; Context for small rarely-changing globals (theme, user); Redux for complex shared state many screens depend on. I don't put everything in Redux.

    05 Next.js & Rendering

    Plain React runs entirely in the browser. Next.js adds routing, server-side rendering, and performance features out of the box. The big win: it can render pages on the server so they load faster and are better for SEO — which matters for marketing/landing pages.

    • CSR (client-side) — browser builds it. Good for app-like screens after login.
    • SSR (server-side) — server builds HTML each request. Good for pages that change and need SEO.
    • SSG (static) — pre-built once at deploy. Fastest; for content that rarely changes.

    ★ yours Your journey app is React + Vite (interactive, behind login); your marketing app is Next.js (public, needs SEO + fast first load). Right tool per job.

    QWhat does Next.js add over plain React?

    ARouting, server-side rendering, and performance features built in. Server rendering means faster loads and better SEO. ★ yours That's why the marketing app uses Next.js.

    QApp Router vs Pages Router?

    ATwo routing systems. Pages is older/file-based; App Router is newer with folders, layouts, and server components by default. ★ yours I work in the App Router — mainly folder structure and layouts.

    QSSR vs SSG vs CSR?

    ACSR = browser builds it; SSR = server builds it per request; SSG = pre-built once at deploy. Landing pages favour SSR/SSG for speed and SEO.

    QServer vs client components? deep · answer honestly

    AIn the App Router, components render on the server by default (smaller bundle). If one needs interactivity (clicks, state, hooks) you mark it "use client". Honest take: I use client components where I need interactivity and I'm still deepening the server-component data flow.

    06 Config-Driven Forms ★ your signature

    Your strongest, most unique topic — own it fully. Instead of hand-coding every form in React, the backend sends a JSON description of the form, and your code reads it and builds the form automatically. The data decides the form, not hard-coded screens.

    // Backend sends this — no React code per product:
const formConfig = [
  { name: "companyName", type: "text",   label: "Company name", required: true },
  { name: "sumInsured",  type: "number", label: "Sum insured",  required: true },
  { name: "droneCount",  type: "number", label: "Number of drones",
    showIf: { field: "product", equals: "Drone" } },   // conditional field
];

// One renderer builds ALL forms by looping over the config:
function FormRenderer({ config, values, onChange }) {
  return config
    .filter(field => isVisible(field, values))   // conditional fields
    .map(field => (
      <Field key={field.name} type={field.type} label={field.label}
        value={values[field.name]} required={field.required}
        onChange={v => onChange(field.name, v)} />
    ));
}

    Why it beats building each form separately: with 20+ insurers and 20+ products, hand-coding every form means thousands of near-duplicate files that each break differently. One tested renderer + per-insurer config = fewer bugs, faster launches, one place to fix things.

    QExplain config-driven forms simply.

    AThe backend sends JSON describing the form; my code reads it and builds the form automatically. The data decides the form, not hard-coded screens.

    QHow does a form render from JSON?

    AThe JSON is a list of fields with type, label, and rules. I loop over it and render the matching component for each. One renderer builds hundreds of forms from different JSON.

    QHow do you handle validation and conditional fields?

    ABoth come from the config. Validation applies as the user types; conditional fields appear/hide based on current answers (e.g. show "number of drones" only for Drone insurance).

    QWhat are cross-field dependencies? deep

    AWhen one field's value affects another — like sum insured changing available add-ons, or one date needing to be after another. The config describes the link and the renderer re-checks it on every change.

    QHow would you add a brand-new product?

    AIn most cases no new UI code — the backend adds the product's field config and the existing renderer builds the form. New products ship without new form code. My job is making sure the renderer supports any new field types or rules.

    07 Performance

    Code splitting / lazy loading — instead of making the user download the whole app upfront, split it into chunks and load each part only when needed. The Quotes screen doesn't download the Proposal screen's code until the user gets there.

    const ProposalPage = lazy(() => import("./ProposalPage"));  // load when used

function App() {
  return (
    <Suspense fallback={<SkeletonLoader />}>   // shown while loading
      <ProposalPage />
    </Suspense>
  );
}

    Skeleton loaders — grey placeholders shaped like the loading content, instead of a blank screen. They make the wait feel shorter and stop layout jumping. ★ yours You matched skeletons to real component shapes so the page doesn't shift.

    QWhat is code splitting and lazy loading?

    ASplitting the app into chunks and loading each only when needed, so first load is faster. In React: React.lazy() + <Suspense>. I split at the route level — each journey is its own chunk.

    QWhat are skeleton loaders and why use them?

    AGrey placeholders shaped like the loading content. They make the wait feel shorter and stop layout shift. ★ yours I matched them to real component shapes.

    QHow did you improve load in your journeys?

    ARoute-level code splitting so each journey loads only its code, plus skeleton loaders so users see structure immediately. Honest framing: practical wins — splitting and placeholders — rather than deep render-profiling.

    QAny other simple performance wins?

    AAvoiding unnecessary re-renders, stable keys in lists, lazy-loading images, and not loading data you don't need yet.

    08 CSS & SCSS Modules

    SCSS is CSS with extra powers — variables, nesting, mixins — that compile to normal CSS. CSS Modules solve a real problem: normal CSS class names are global, so two files using .button can clash. CSS Modules scope each class to its own file automatically.

    import styles from "./Button.module.scss";

function Button() {
  return <button className={styles.primary}>Buy</button>;
  // styles.primary becomes a unique name — no clashes
}

    ★ yours The migration: the app had 144 stylesheets using global CSS, causing clashes and hard-to-trace overrides. You migrated them to SCSS Modules across ~20 journeys, so each component's styles are isolated — fewer visual bugs.

    QSCSS vs plain CSS?

    ASCSS adds variables, nesting, and mixins that compile to normal CSS — easier to organise and keep consistent.

    QWhat problem do CSS Modules solve?

    ANormal CSS class names are global and can clash. CSS Modules scope each class to its file so styles can't leak or collide — huge on a large multi-dev app.

    QTell me about the stylesheet migration.

    A144 global-CSS stylesheets were causing clashes and tricky overrides. I migrated them to SCSS Modules across ~20 journeys so each component's styles are isolated — fewer visual bugs.

    QWhat is CSS specificity?

    AThe rulebook for which style wins. IDs beat classes, classes beat tags, inline beats all. Overly specific selectors cause "why won't this apply" fights; CSS Modules reduce that by keeping scope local.

    09 Testing

    You write tests so that when you change code, you know you didn't break something. Unit test = one small function in isolation; component test = render a component and check it behaves on interaction. Vitest runs the tests; React Testing Library lets you interact the way a user would.

    test("shows an error when a required field is empty", () => {
  render(<FormRenderer config={[{ name: "name", type: "text", required: true }]} />);
  fireEvent.click(screen.getByText("Submit"));
  expect(screen.getByText("This field is required")).toBeInTheDocument();
});

    QWhy write tests?

    ASo changing code doesn't silently break something. Tests catch regressions early. ★ yours With many insurers sharing one renderer, tests on shared components protect everyone.

    QUnit vs component testing?

    AUnit tests one small function in isolation; component test renders a component and checks behaviour on interaction. I mostly write component tests for shared UI.

    QWhat do Vitest and RTL do?

    AVitest runs the tests and reports results; RTL renders components and lets me interact like a user — find a field, type, click, check the result.

    QWhat do you actually test?

    10 Routing, APIs & Lead Handoff

    React Router shows different components for different URLs without a full reload. A dynamic route has a changing part: /quote/:insurerId — one route serves 20+ insurers. When calling an API, always handle three states: loading, success, error.

    function QuotePage({ insurerId }) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    setLoading(true);
    fetch(`/api/quote/${insurerId}`)
      .then(res => res.json())
      .then(setData)
      .catch(() => setError("Could not load quote"))
      .finally(() => setLoading(false));
  }, [insurerId]);

  if (loading) return <SkeletonLoader />;
  if (error)   return <p>{error}</p>;
  return <Quote data={data} />;
}

    ★ yours Lead handoff: the Next.js marketing app captures a lead; when the user moves to buy, that data is passed securely into the React journey app so they don't re-enter it. You built the frontend side; encryption was shared with backend.

    QWhat does React Router do?

    AHandles navigation in a single-page app — different components for different URLs, no full reload.

    QWhat is a dynamic route?

    AA route with a variable part like /quote/:insurerId. ★ yours That's how one route handles 20+ insurers — the ID tells the page which data to load.

    QHow do you integrate a REST API and handle loading/errors?

    ACall the endpoint in an effect/handler, await it, store the result in state, and handle loading, success, and error — a loader while loading, a clear message on error.

    QExplain the lead handoff between your two apps.

    13 Rapid-Fire

    One-liners for last-minute revision.

    • Virtual DOM — a lightweight copy of the page; React compares it to find the minimum changes, so updates are fast.
    • Props drilling — passing data through many layers to reach a deep component; Context or Redux avoids it.
    • Debounce — wait until the user stops typing before firing (e.g. search).
    • Throttle — run an action at most once every X ms (e.g. on scroll).
    • CORS — a browser security rule about which sites can call which APIs; the server must allow your origin.
    • REST status codes — 200 OK, 201 created, 400 bad request, 401 unauthorized, 403 forbidden, 404 not found, 500 server error.
    • GET vs POST — GET reads data (no body); POST sends data to create/change.
    • null vs undefined — undefined = never set; null = deliberately empty.
    • Git merge vs rebase — merge joins branches keeping history; rebase replays your commits on top for a cleaner line. Don't rebase shared branches.
    • Promise states — pending, fulfilled, rejected.
    • Sync vs async — sync runs line by line and waits; async starts slow work and handles the result later.
    • JSX — HTML-like syntax inside JavaScript that React turns into UI.
    • Fragment <> — group elements without an extra wrapper div.
    • Pure function — same input always gives the same output, no side effects.
